Part 3 — System Design: Relay Notification Infrastructure
3.1 Project Overview
Project: Relay — Multi-Tenant Notification Infrastructure Prototype
Repository: https://github.com/ScrappyAT/relay-notification-system
Status: Technical design, working prototype, automated tests, and local admin dashboard completed; walkthrough and mock technical interview pending.

Relay is a notification infrastructure prototype built for the Part 3 system design task. It accepts email and SMS notification requests, persists them, places work onto background queues, and processes delivery through simulated providers. The implementation explores idempotency, tenant rate limits, preferences, backpressure, recovery, observable failures, and bounded retries. It is a local prototype, not a production-ready multi-tenant service: authentication and authorization are not implemented, and provider acceptance does not prove recipient delivery.

3.3 Working Prototype
Source repository: https://github.com/ScrappyAT/relay-notification-system
Project setup: README.md
Learning log: LEARNING-LOG.md

Implemented prototype capabilities:
- Express/TypeScript notification ingestion with PostgreSQL durability and a transactional outbox.
- Redis/BullMQ email and SMS background processing with worker leases and recovery.
- Idempotency handling for repeated requests and conflict detection for mismatched requests.
- Tenant-scoped rate limiting, admission/backpressure controls, and recipient email/SMS preferences.
- Simulated provider acceptance, permanent and transient errors, timeout/unknown outcomes, bounded retries, and failure recording.
- API health/readiness and Prometheus-compatible operational metrics.
The prototype uses simulated providers; it does not send real email or SMS. It does not guarantee exactly-once external delivery.

The three documented k6 scenarios measured durable notification acceptance of approximately 1.70 requests/s (baseline), 4.13 requests/s (ramp-up), and 3.30 requests/s (spike) in the tested setup. The report distinguishes accepted requests from rate-limited and overload-shed requests; these measurements do not validate the 50-million/day design target.

Failure scenarios include provider HTTP 400/429/503 errors, simulated timeouts, worker recovery, and Redis interruption. At the dashboard publication stage, 140/140 automated tests were reported passing, including the original 95 backend tests; backend and dashboard builds were also reported passing.
